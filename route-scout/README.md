# route-scout — 牽引向けルート下見ツール

牽引車のドライバーが出発前に、走行ルート上の「狭くて通れない可能性がある区間」だけを
把握するための道具。設計は引き継ぎ仕様「牽引向けルート下見ツール 実装引き継ぎ仕様」に従う。

**幅員データは候補を絞るためだけに使う。** 電柱・路上駐車・カーブミラーの張り出し・
内輪差はデータに含まれないため、通行可否の最終判断は必ず人間がストリートビューで行う。

## 使い方

Node 18 以上。依存パッケージなし、ビルド工程なし。

### ステップ1: 1 地点の幅員を見る

```
node route-scout/bin/probe.mjs 43.5551,142.4695 43.5560,142.4700
node route-scout/bin/probe.mjs --file points.txt        # 1 行 1 地点、# 以降はコメント
node route-scout/bin/probe.mjs --health 43.5551,142.4695 # rnkWidth 属性の生存確認つき
```

座標は Google マップからコピーした「緯度,経度」の順でそのまま貼れる。
半径内の候補を近い順に全部出すので、並走する路地を拾っていないかをその場で確かめられる。

### ステップ2〜5: ルートを走査する

```
node route-scout/bin/scan.mjs --coords "43.5551,142.4695 43.5551,142.4795"
node route-scout/bin/scan.mjs --polyline '_p~iF~ps|U...'
node route-scout/bin/scan.mjs --geojson route.json --sv-key "$MAPS_KEY"
```

`--sv-key` はパノラマの有無と撮影日の照会に使う。この照会は課金もクォータ消費もしない
（画像を読み込んだときだけ消費される）。渡さなければ一切外部キーなしで完結する。

主な調整つまみ:

| オプション | 既定 | 意味 |
| --- | --- | --- |
| `--radius <m>` | 20 | スナップの距離閾値。**実データで要調整** |
| `--angle <deg>` | 45 | ルートと道路中心線の向きのずれ許容量 |
| `--step <m>` | 10 | サンプリング間隔 |
| `--min-run <m>` | 0 | これより短い区間を捨てる |
| `--endpoint <url>` | 地理院 | タイルの取得先の差し替え |

### ステップ6: 出発地・目的地からルートを取る

```
export ROUTE_SCOUT_ROUTES_KEY="..."
node route-scout/bin/scan.mjs --from "旭川駅" --to "43.5551,142.4695"
```

出発地・目的地は「緯度,経度」でも住所でも渡せる。**ここだけが課金されうる。**
実行後に encoded polyline を出力するので、閾値を変えて掛け直すときは
`--polyline` を使えば再取得せずに済む。

課金 SKU を Compute Routes Essentials（月10,000無料）に留めるため、
フィールドマスクは polyline・距離・所要時間の 3 つに絞り、
`routingPreference` は `TRAFFIC_UNAWARE` を既定にしてある。
`legs.steps` や渋滞考慮を足すと上位 SKU に跳ねるので、安易に増やさないこと。
この対応関係は引き継ぎ仕様の記載に基づくもので、一次ソースは未確認
（下記のとおり `developers.google.com` に到達できなかった）。

### テスト

```
node route-scout/test/run.mjs
```

ネットワークにも npm にも依存しない 27 件。MVT の復号、測地計算、polyline、判定、

## 検証済みのこと / していないこと

**検証済み**

- MVT デコーダを参照実装 `@mapbox/vector-tile` と実タイル 1 枚（182KB・20 レイヤ）で全件照合。
  フィーチャ 2,759 件 / プロパティ値 13,597 件 / 座標 17,142 点が完全一致。
  唯一の差は、参照実装がフィーチャ 0 件のレイヤを捨てるのに対しこちらは残すこと（意図的）。
  再実行は `node route-scout/test/crosscheck.mjs`（別途 npm での導入が必要）。
- 負の int64 属性の復号。10 バイトの varint を上位ビットごと扱わないと符号が落ちる。
  参照実装との照合で実際にこのバグが出たので、`test/run.mjs` に固定してある。
- 取得 → gzip 展開 → 復号 → スナップ → 統合 → リンク生成 → 表示の通し動作を、
  ローカルに立てた擬似タイルサーバで確認。緯度経度⇄タイル座標の変換は
  擬似サーバ側を別の式で独立に書いて突き合わせた（照合率 100%）。
- ルートに直交する細道を誤って警告しないこと（向きによる絞り込み）。

**検証していないこと（実機での確認が必要）**

- 地理院ベクトルタイルの実データに対する動作一切。
  このツールを書いたクラウドセッションからは `cyberjapandata.gsi.go.jp` への通信が
  組織のegressポリシーで遮断されていたため、実タイルを 1 枚も取得できていない。
- `rnkWidth` の値が牽引の実感と合うかどうか（ステップ1の完了条件）。
- Routes API の実キーでの疎通と、実際に Essentials の無料枠内で課金されるかどうか。
- 生成したリンクを開いたときに進行方向を向いているか（ステップ4の完了条件）。
- 引き継ぎ仕様に書かれた外部仕様の一次ソース再確認。`developers.google.com` と
  `www.gsi.go.jp` も同じく遮断されていたため、エンドポイント URL・`rnkWidth` の区分値・
  Maps URLs のパラメータ・料金は**すべて引き継ぎ仕様の記載をそのまま採った**。

## 構成

```
lib/mvt.mjs        MVT (protobuf) デコーダ。依存なし
lib/geo.mjs        測地計算とタイル座標変換
lib/polyline.mjs   Google encoded polyline の符号化・復号
lib/width.mjs      幅員プロバイダ（差し替え可能）と判定
lib/svlink.mjs     Maps URLs とメタデータ照会
lib/routing.mjs    ルート取得（Google Routes API）。キーはサーバー側にだけ置く
lib/scout.mjs      走査本体（スナップ → 判定 → 統合 → リンク）
lib/cache-node.mjs タイルのローカルキャッシュ（Node 用）
bin/probe.mjs      ステップ1 の検証ハーネス
bin/scan.mjs       ステップ2〜6
test/run.mjs       オフラインのテスト
```

すべて素の ES モジュールで、ビルド工程を持たない。最終的に GitHub Pages 上の
静的ページからそのまま読み込めるようにするため、`lib/` は Node 固有の API を使わない
（`cache-node.mjs` だけは名前のとおり Node 専用）。

## 設計上の判断

- **幅員プロバイダをインタフェースで切ってある。** 地理院ベクトルタイルは提供実験で、
  終期未定・URL や属性が変わりうる。`GsiVectorTileProvider` を差し替えれば OSM などに
  移れる。`--endpoint` で取得先だけ変えることもできる。
- **`healthCheck()` が `rnkWidth` の生存を見る。** 属性が消えたら `probe --health` が
  NG を返して即座に気づける。
- **区分 5（その他）と 6（不明）は「問題なし」と言わない。** どちらも幅員の実測ではないので
  UNKNOWN 扱いにし、警告も出さない代わりに「データなし」と明示する。
  データが無いことを大丈夫と読ませないため。
- **最近傍だけでスナップしない。** ルートの進行方位と向きが揃った線分を優先する。
  単純な最近傍だと並走する路地を拾って誤警告になり、警告一覧が信用されなくなる。
  揃った候補が無いときは最近傍に落として、その旨を出力に印として残す。
- **「不明」が 30m 以内で挟まる場合は前後を繋ぐ。** データの穴で 1 つの狭隘路が
  2 件に割れると一覧が読みにくいため。前後の重大度が同じときだけ繋ぐ。
- **タイルをローカルにキャッシュする。** 地理院タイルの取得は課金対象ではないが
  サーバー負荷への配慮。Google のコンテンツと違いキャッシュの制限はない。
