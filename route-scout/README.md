# route-scout — 牽引向けルートツール

出発地と目的地から、**できるだけ幅員の広い道を通るルート**を作る。
できたルートは Google マップに渡して、走行中の案内はそちらに任せる。

**自前で経路探索はしない。** Google に引かせたルートを幅員で採点し、狭い区間の近くにある
太い道の上に経由点を置いて引き直す、を数回繰り返す。ベクトルタイルには道路の接続情報が
入っておらず、一方通行や進入禁止も含まれないので、道を繋ぐ仕事と交通規則は Google に任せる。

**広い道になる保証はない。** 良くなったときだけ採用する、という作り。
そして幅員データには電柱・路上駐車・カーブミラーの張り出し・内輪差が含まれないため、
**通行可否は保証できない**。残った狭い区間は人間がストリートビューで確かめる。

## 使い方

Node 18 以上。依存パッケージなし、ビルド工程なし。

### 画面から使う

**キーも設定も要らない。** `start-windows.bat` をダブルクリックするか、リポジトリ直下で:

```
python -m http.server 8080 --directory .
```

ブラウザで `http://localhost:8080/route-scout/` を開く
（`file://` では ES モジュールが動かないので必ず HTTP 経由で）。

出発地と目的地を入れて「広い道のルートを調べる」だけ。ルートの取得元は既定で
**キー不要モード**（OSRM 公開デモ + Nominatim）になっている。公開デモなので
本番運用には使えず、有料道路などの指定も効かない。

公開するときは取得元を「中継ごしに Google Routes API」に切り替える。
キーはブラウザに置かず、中継に持たせる:

```
# 手元で中継を立てる
ROUTE_SCOUT_ROUTES_KEY="..." node route-scout/proxy/local.mjs
# 画面の「設定」に http://127.0.0.1:8787/ を入れる
```

本番は `proxy/worker.mjs` を Cloudflare Workers に貼り、`ROUTES_API_KEY` を Secret に登録。
`ALLOW_ORIGIN` は公開先のオリジンに絞ること。ビルド工程は不要。

### コマンドラインから使う

```
# 1 地点の幅員を見る（判定が実感と合うかの確認）
node route-scout/bin/probe.mjs 43.5551,142.4695 --health

# 決まった経路を走査する
node route-scout/bin/scan.mjs --coords "43.5551,142.4695 43.5551,142.4795"

# 出発地・目的地から取得して走査する（課金はここだけ）
ROUTE_SCOUT_ROUTES_KEY="..." node route-scout/bin/scan.mjs --from "旭川駅" --to "..."
```

### テスト

```
node route-scout/test/run.mjs
```

ネットワークにも npm にも依存しない 36 件。MVT の復号、測地計算、polyline、判定、
区間統合、誤警告の抑制、Routes API の要求内容、広い道への寄せ、採点、キー不要の
ルート取得までを固定データで確認する。

## 検証済みのこと / していないこと

**検証済み**

- MVT デコーダを参照実装 `@mapbox/vector-tile` と実タイル 1 枚（182KB・20 レイヤ）で全件照合。
  フィーチャ 2,759 件 / プロパティ値 13,597 件 / 座標 17,142 点が完全一致。
  唯一の差は、参照実装がフィーチャ 0 件のレイヤを捨てるのに対しこちらは残すこと（意図的）。
  再実行は `node route-scout/test/crosscheck.mjs`（別途 npm での導入が必要）。
- 負の int64 属性の復号。10 バイトの varint を上位ビットごと扱わないと符号が落ちる。
  参照実装との照合で実際にこのバグが出たので、`test/run.mjs` に固定してある。
- 取得 → gzip 展開 → 復号 → スナップ → 統合 → リンク生成 → 表示の通し動作を、
  ローカルに立てた擬似タイルサーバで確認。緯度経度⇄タイル座標の変換は
  擬似サーバ側を別の式で独立に書いて突き合わせた（照合率 100%）。
- ルートに直交する細道を誤って警告しないこと（向きによる絞り込み）。

- 地理院ベクトルタイルの実データ（2026-09-24、ブラウザから直接）。CORS ヘッダ付きで取得でき、
  復号と `rnkWidth` の読み出しが動く。美瑛駅→白金温泉 20km を 69 枚のタイルで走査し照合率 100%。
- road レイヤには道路縁（ftCode 22xx）や徒歩道（27 2x）も入っている。これを候補から外さないと
  道路縁に吸着して 1 割が「データなし」になる（実タイルで発見し、修正済み）。
- キー不要モード（OSRM 公開デモ + Nominatim）の実接続。
- `rnkWidth` と `rdCtg` の区分値、Maps URLs の `waypoints` 上限を一次ソースで再確認
  （地理院 attribute.docx、Google Maps URLs「Get started」）。

**検証していないこと（実機での確認が必要）**

- `rnkWidth` の値が牽引の実感と合うかどうか（ステップ1の完了条件）。
- Routes API の実キーでの疎通と、実際に Essentials の無料枠内で課金されるかどうか。
- 生成したリンクを開いたときに進行方向を向いているか（ステップ4の完了条件）。
- Routes API のエンドポイント URL・フィールドマスク・料金は引き継ぎ仕様の記載のまま（未確認）。
- 経由点が実際に置かれるケースの通し動作（実ルートでは狭い区間が少なく、まだ寄せが発動していない）。

## 構成

```
lib/mvt.mjs        MVT (protobuf) デコーダ。依存なし
lib/geo.mjs        測地計算とタイル座標変換
lib/polyline.mjs   Google encoded polyline の符号化・復号
lib/width.mjs      幅員プロバイダ（差し替え可能）と判定
lib/svlink.mjs     SV リンク、Google マップへの経路受け渡し URL
lib/routing.mjs    ルート取得（Google Routes API）。キーはサーバー側にだけ置く
lib/routing-osrm.mjs キー不要のルート取得（OSRM 公開デモ + Nominatim）
lib/scout.mjs      走査本体（スナップ → 判定 → 統合 → リンク）
lib/widen.mjs      広い道への寄せ（採点 → 経由点の選定 → 引き直し）
lib/cache-node.mjs タイルのローカルキャッシュ（Node 用）
bin/probe.mjs      1 地点の幅員を見る検証ハーネス
bin/scan.mjs       決まった経路の走査
proxy/worker.mjs   ルート取得の中継（Cloudflare Workers 用・単体で完結）
proxy/local.mjs    同じ契約を手元で動かす版
index.html         画面。出発地・目的地を入れるだけ
start-windows.bat  ローカルサーバをダブルクリックで起動（Windows）
CLAUDE.md          作業を引き継ぐセッション向けの申し送り
test/run.mjs       オフラインのテスト
```

すべて素の ES モジュールで、ビルド工程を持たない。最終的に GitHub Pages 上の
静的ページからそのまま読み込めるようにするため、`lib/` は Node 固有の API を使わない
（`cache-node.mjs` だけは名前のとおり Node 専用）。

## 設計上の判断

- **幅員プロバイダをインタフェースで切ってある。** 地理院ベクトルタイルは提供実験で、
  終期未定・URL や属性が変わりうる。`GsiVectorTileProvider` を差し替えれば OSM などに
  移れる。`--endpoint` で取得先だけ変えることもできる。
- **`healthCheck()` が `rnkWidth` の生存を見る。** 属性が消えたら `probe --health` が
  NG を返して即座に気づける。
- **区分 5（その他）と 6（不明）は「問題なし」と言わない。** どちらも幅員の実測ではないので
  UNKNOWN 扱いにし、警告も出さない代わりに「データなし」と明示する。
  データが無いことを大丈夫と読ませないため。
- **最近傍だけでスナップしない。** ルートの進行方位と向きが揃った線分を優先する。
  単純な最近傍だと並走する路地を拾って誤警告になり、警告一覧が信用されなくなる。
  揃った候補が無いときは最近傍に落として、その旨を出力に印として残す。
- **「不明」が 30m 以内で挟まる場合は前後を繋ぐ。** データの穴で 1 つの狭隘路が
  2 件に割れると一覧が読みにくいため。前後の重大度が同じときだけ繋ぐ。
- **タイルをローカルにキャッシュする。** 地理院タイルの取得は課金対象ではないが
  サーバー負荷への配慮。Google のコンテンツと違いキャッシュの制限はない。
- **自前で経路探索しない。** ベクトルタイルには道路の接続情報が入っておらず、
  一方通行・進入禁止・通行止めも含まれない。幅員だけで経路を引くと逆走ルートが出る。
  代わりに「狭い区間の近くにある太い道」に経由点を置き、道を繋ぐ仕事と交通規則の遵守は
  Google に任せる。接続性が取れるかどうかという賭けも避けられる。
- **経由点の候補は低ズーム（ZL14）で探す。** 低ズームのタイルは細い道が間引かれていて、
  太い道だけが残る。こちらが欲しいものと一致するうえ、読むタイルが減る。
- **良くなったときだけ採用する。** 引き直した結果を採点し、改善しなければ捨てて次の候補へ。
  遠回りは `detourPenaltyPerKm` でつらさに換算して比べる（既定は 1km = 狭い道 100m 相当）。
- **課金の上限を持つ。** ルート取得の回数は `maxRouteCalls` で頭打ちにする（既定 4 回 + 初回）。
  1 ルートあたり最大 5 回なので、無料枠 10,000 でおよそ 2,000 ルート。

## 未決事項

- **公開形態**: 無料公開か、mono labo 商品購入者向けの付帯サービスか、独立した有料サービスか。
- **判定と採点のつまみ**: スナップ半径（既定 20m）、向きのずれ許容（既定 45度）、
  判定閾値（`rnkWidth ≦ 1`）、遠回りの重み（既定 100）。いずれも実走検証で詰める。
  画面の「設定」から変えられるようにしてある。
- **Maps URLs の waypoints 上限**: モバイルブラウザは 3 箇所、それ以外は 9 箇所（公式ドキュメント）。
  画面は幅で切り替えている。超える場合の間引き方は決まっていない（今は先頭から切っている）。
- **幅員以外の判定**: 高さ制限・重量制限・勾配は今のデータに入っていない。
  牽引で本当に効くのは「狭い × 曲がる」の組み合わせなので、
  ルートの座標から曲率を出して重みに入れる案がある（追加データ不要）。
